# Architecture

[README](../README.md) | [繁體中文 README](../README.zh-TW.md)

Mobile-first PWA for keeping track of physical Pokémon TCG cards. Photograph a card, confirm what was read, and it lands in a binder. Deployed to GitHub Pages under `/card-binder/` from `main`.

## Design

- Neutral grays only (`--bg`, `--surface`, `--ink`, `--soft`, `--line`, `--tint` in `src/index.css`); the card photos are the only color. System font, no emoji.
- Home (`Binder.jsx`): tabs 系列 / 稀有度 / 自訂. 系列 is a shelf of binder covers, 2 columns (3 from 600px): each cover shows the set's highest-rarity card (by `RARITIES` order, lowest number on ties) on a white cover with a left spine, the set code, language, `owned / total`, duplicates and a thin progress bar. 稀有度 and 自訂 are plain rows with counts. A full-width 掃描 button floats at the bottom.
- Binder pages (`BinderPages.jsx`): 3x3 pockets per white sheet, swiped horizontally with scroll snap, plus 上一頁 / 下一頁 and `page / pages`. In a set with a known total, every number from 1 to the total has a fixed pocket in order (card 040 sits in the 4th pocket of page 5); empty pockets show the number in light gray; cards numbered above the total (secret rares) follow after the last numbered pocket. With a rarity filter, or in rarity, tag and Pokemon lists, cards fill the pockets in order without gaps. Filled pockets get a faint diagonal sheen like a plastic sleeve and a quantity badge when more than one copy is owned. Below a set, 還缺 N 張 lists the missing numbers as ranges.
- Card page (`CardDetail.jsx`): large photo, name (tap to list every card of that Pokemon), set (tap to open its binder), number, rarity, quantity stepper, tags, edit, delete.
- Installed PWA: `overscroll-behavior-y: none` on `html` and `body` under `display-mode: standalone`; layout heights use `100dvh` and safe-area insets.

## Scanning

- `Scanner.jsx`: rear camera (`getUserMedia`, ideal 1920x1080) under a card-shaped frame (63:88, `min(92vw, (100dvh - 150px) * 63 / 88)`, 359x501 on a 390x844 screen) with the rest dimmed and no inner boxes; the hint 「卡片放進框內就好，不用對齊」 sits on top of the camera image. The card only has to be roughly inside the frame: the reader searches wide areas instead of fixed boxes. 相簿 loads a photo instead; it can be dragged (one pointer) and zoomed (two pointers or the mouse wheel). The camera is requested with the rear-camera constraints first and, on any error other than a refused permission, once more with plain `video: true`. Failures show the reason from the error name with 重試 (re-request) and 相簿 still available: NotAllowedError or SecurityError (permission refused; allow the camera in the site settings), NotFoundError (no camera), NotReadableError or AbortError (camera busy in another app), otherwise the raw error name; a browser without `getUserMedia` gets 「這個瀏覽器不支援相機，請改用 Safari 或 Chrome 開啟」 (typical for in-app browsers such as LINE), or a non-https note when `isSecureContext` is false.
- On capture the camera video is paused, so the captured frame stays on screen and the phone can be put down; 「辨識中，可以放下手機」 shows in a small panel under the frame instead of covering it.
- On capture the frame is mapped back to video or photo pixels (object-fit cover for the video, the transformed image box for photos) and cropped to at most 1000px wide.
- Card edges (`cardDetect.js`, no OpenCV): the frame crop is shrunk to 320px wide, blurred and run through Sobel gradients. For each side, every scanline in the middle 76% collects all local gradient maxima within the outer 42% that run along that side; RANSAC (2px tolerance, slope up to 0.35) pulls out up to four lines per side and keeps the outermost one that spans at least 30% of the scanlines, because the silver card border against a light table is weaker than the edges of the artwork inside the card. The four lines are intersected; the quad must cover a quarter of the frame and be within -20% / +25% of the 63:88 card ratio. It is expanded by 3% on every side so the bottom line with the card number is never cut, then warped (homography, bilinear) to 900x1257. The saved photo is that straightened card at 630x880; when no card is found, the frame crop is used as is. On the sample photos with the frame 8%, 20% and 35% larger than the card, all 15 crops were found (about 30 ms detect plus 20 ms warp in Node).
- Text (`ocr.js`, `ocrWorker.js`): PaddleOCR PP-OCRv6 tiny (one model for Traditional and Simplified Chinese, Japanese and English) through `ppu-paddle-ocr/web` and ONNX Runtime Web, in a module Web Worker so the page stays responsive. The worker forces the `wasm` execution provider and the `cross-line` recognition strategy: by default the library prefers WebGPU when `navigator.gpu` exists, which on iPhone Safari took about 12 s per card; with WebAssembly the same build read a card in 1.1 s in the in-app browser (6.4 s before). `cross-line` batches lines into fewer recognition calls (about 20% faster in a single-thread WebAssembly run in Node) and cost one Pokémon out of 30 test reads; the detector keeps its default 960px cap because 800 and 640 lost card numbers. The detection and recognition models and the dictionary (6.4 MB, Apache-2.0, `public/models/` with `LICENSE` and `NOTICE`) are served from this site and cached by the service worker in `ocr-models`; the ONNX Runtime WebAssembly comes from jsDelivr (`ort.env.wasm.wasmPaths` set by the library, about 6.7 MB compressed, cached in `ocr-runtime`). The bundler also emits a copy of that wasm into `dist/assets`, which the app does not load. The detector finds text anywhere, so nothing needs to be aligned. The straightened card is read first; when no three-digit number was found, the unstraightened frame crop is read too and its text is added.
- `parse.js`: `parseCode` looks at each line for `NNN/TTT` (three-digit number preferred, `/` also read as `|`, `l` or `I`) and takes a rarity only from the same line right after the number (C, U, R, RR, RRR, AR, SAR, SR, UR, HR, ACE, PR). `parseDex` reads the printed Pokédex number (全國圖鑑No.0790, NO. 789) and is used before name matching. `matchName` joins CJK characters split by spaces, compares tokens with every species name (bigram Dice, plus per-character overlap for Chinese and Japanese), prefers earlier tokens, needs 0.6 (0.8 for English) and returns nothing when the two best species are within 0.05. `detectLang` says ja when there is kana, zh with four or more Han characters, en with four or more Latin words. The set code sits in a small inverted box (M6a) whose 6 looks like b, so OCR returns MbaF, JbaF or baF. `parseSetCode` takes the text before the number on the number line, drops a leading regulation mark (D to J) and a trailing single capital (F), maps look-alike letters in the digit position to digits (b to 6, O/o/D/Q to 0, l/I/i to 1, S/s to 5, Z/z to 2, B to 8, g/q to 9), then matches the set codes already in the binder (exact, or by the last two characters, with the same look-alike mapping); without a match it keeps a result shaped like `[A-Z]{1,3}\d{1,2}[a-z]?`, otherwise nothing, and the editor falls back to the last saved set code. With M6a already in the binder this found the set on 10 of 30 test reads (it needs the number line to be read at all); with an empty binder the Mewtwo photo still gave M6a from MbaF.
- The confirm screen shows, in small gray text, the recognition time, the number of OCR passes and the model load time, to measure real phones.
- Measured in Node with the same models, detection and parsing on the five sample photos, each with the frame matching the card, 15% and 35% larger, 10% smaller (edges cut) and shifted 8% right or down (30 reads): number correct 21, wrong 0; Pokémon correct 21, wrong 0; card found 29; 0.3 to 2.3 s per card. In the in-app browser (hidden pane, production build, whole photos without any alignment) four of the photos gave the right number, name and language except a missing number on the angled dark card and RR read as R; each read took 8 to 24 s there, including the first model download. The blurry photo fails every time. The confirm screen always shows what was read and lets the user fix it.

## Editing and data

- `CardEditor.jsx`: set code, language (繁中 / 日文 / 英文), number, total, rarity, name with autocomplete from `names.json` in the chosen language, quantity. A new card starts from what OCR read (number, total, rarity, Pokémon from the Pokédex number or the name, language from the script) and takes the set code from the last saved card; total and language fall back to the last saved card too (`localStorage` key `lastSet`), so a pack of one set only needs the number. 儲存，繼續掃描 returns to the camera.
- `db.js` (Dexie, IndexedDB database `card-binder`): table `cards` with `lang`, `setCode`, `number` (3 digits), `total`, `rarity`, `name`, `dex`, `qty`, `tags`, `photo` (Blob), `createdAt` and `setKey` = `lang|setCode|total`. Saving a card whose set, number and rarity already exist adds to its quantity instead of a new entry.
- Backup (`Backup.jsx`): everything stays in the browser on this device. 匯出備份檔 downloads `card-binder-YYYY-MM-DD.json` with photos as data URLs; 匯入備份檔 replaces all cards after a confirmation. The page shows storage use and can ask the browser for persistent storage.
- `src/data/names.json`: `[dex, zh, ja, en]` for all 1025 species from PokeAPI `pokemon_species_names.csv` (zh-Hant, ja-Hrkt, en), built by `npm run data:names`.

## PWA

- `vite.config.js`: generated service worker with `skipWaiting`, `clientsClaim` and `navigateFallback`; `src/pwa.js` checks for updates on load, when the app becomes visible, on `pageshow` from bfcache and every 30 minutes, and reloads on `controllerchange` after the first install.
