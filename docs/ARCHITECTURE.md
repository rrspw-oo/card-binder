# Architecture

[README](../README.md) | [繁體中文 README](../README.zh-TW.md)

Mobile-first PWA for keeping track of physical Pokémon TCG cards. Photograph a card, confirm what was read, and it lands in a binder. Deployed to GitHub Pages under `/card-binder/` from `main`.

## Design

- Visual language (`src/index.css`): light colors only (the user turned down dark panels). A pearl gray background (`--bg` #ebebf0, with a lighter #f8f7fc fade over the top 380px), white rounded panels (16 to 22px radius, `--shadow-panel`), black as the main accent (`--ink`) and one signature accent, an iridescent holo gradient (`--holo`: pink, gold, mint, blue, lilac) used only in thin lines and small fills: the drifting 1.5px border of the home overview and the set cover (8s loop, stopped under reduced motion), progress bars, the set progress ring (`#ring-holo`) and a blurred glow under the 掃描卡片 button, so the app echoes the card shine without becoming colorful, gray secondary text (`--soft`, `--faint`). Cards are drawn at 63:88 with the real card corner radius (`--card-radius`, 4.8% / 3.4%) and a soft shadow (`.card-img`), so they read as physical cards; the photos are the only color. System font, large titles (34px home, 21px section titles), tabular numbers for counts. Sub pages share `PageHead.jsx`: a sticky translucent header with a chevron back button naming the previous page, the title and an optional action. Icons are inline SVG strokes in `Icon.jsx`; no emoji. Pages fade up on entry (0.32s). Under `prefers-reduced-motion` only the large movements stop (page entry, the confirm sheet sliding up, the tilt hint, toasts, corner and dot transitions); the card shine still plays, because the user asked for it and it does not move the layout (this Mac reports reduced motion, and the earlier blanket rule switched every animation off).
- Card shine (`TiltCard.jsx`, chosen by the user from six variants): when a card page opens or the confirm sheet shows a card, RR and rarer cards (RR, RRR, AR, SAR, SR, UR, HR, ACE; `isPremium` in `parse.js`) get a rainbow holo sweep (`.shine-holo`, color-dodge, 1.5s, starting after 0.05s) plus a warm gold light running once around the edge (`.shine-ring`, conic gradient on an animated `@property` angle, masked to a 5px ring, 1.3s, starting after 0.15s); other cards (C, U, R, PR or no rarity) get six small four-point stars that twinkle one after another (`.shine-sparks`, 0.7s each, 120ms apart, the first after 60ms). The effect plays once per mount; the card page remounts it per card (`key`).
- Home (`Binder.jsx`), 我的收藏, fits one screen and never scrolls (`.page.home`: a 100dvh flex column, 92px plus the safe area left for the floating button): a 30px title with a 備份 pill; the overview panel with the holo border, a 收藏總覽 eyebrow and three 30px numbers (張卡 = total copies, 隻寶可夢 = distinct Pokédex numbers, or names when no number, 系列 = distinct sets; tapping 隻寶可夢 opens `PokemonList.jsx`, a grid of each Pokémon with its rarest card and copy count); a search field that filters by name, set code, exact card number, `set number` or tag and shows the results in a panel that scrolls on its own; a row of rarity (rarest first) and tag pills with counts that scrolls sideways; 最近收進, a panel with a horizontal rail of the 12 newest cards (92px wide); 卡冊, a panel that takes the remaining height and scrolls inside when there are more sets than fit, one row per set separated by hairlines, with a fan of its three rarest cards, set code, language, set name, progress bar and `owned / total`, newest set first. On screens under 740px tall the eyebrow and rail names are hidden and the rail cards shrink to 68px; at 375x667 the 卡冊 panel is 126px and its first row is partly visible. With no cards, the sections are replaced by a drawn stack of card outlines and 開始你的卡冊 (the explanation paragraph under it was removed at the user's request). A black 掃描卡片 pill floats at the bottom. Every area sits in its own white panel (24px radius, a header row with title and count) so the zones read clearly.
- Binder pages (`BinderPages.jsx`): styled as a premium binder in light colors. A white cover panel with the drifting holo border on top (`ListView.jsx`) shows the set code in 32px, set name and language, 已收 / 還缺 / 重複 counts and a holo gradient progress ring with the percentage (the user asked for light colors throughout). Each page is a white sheet (the user turned down a dark one) with three punched holes down the left edge and 3x3 clear pockets: a light gray fill (`--pocket`), a 1px edge, a sleeve opening line near the top and a diagonal sheen, with the number in light gray in empty pockets. RR and rarer cards get a gold pocket edge with a soft glow. Pockets shrink slightly while pressed. Pages swipe horizontally with scroll snap, with page dots (up to 20 pages; the active dot is a wider black pill and tapping a dot turns to that page) and `page / pages` under them. In a set with a known total, every number from 1 to the total has a fixed pocket in order (card 040 sits in the 4th pocket of page 5); cards numbered above the total (secret rares) follow after the last numbered pocket. A black quantity badge sits on the top right corner when more than one copy is owned. A set opens on the page holding the most recently added card (by `createdAt`). Rarity, tag and Pokémon lists are a 3-column card grid with name, set, number and copies instead of pockets.
- Card page (`CardDetail.jsx`): only the graded card case (slab), filling the screen without vertical scrolling (`.page.is-fit`: a 100dvh flex column; the well is a size container and the card is `min(84cqw, 100cqh * 63 / 88)` wide, so it is centered and fits both the width and the height; at 462x880 it is 309px wide with equal gaps on both sides). The case holds a label strip on top (name in 22px, tap to list every card of that Pokémon; set code and set name, tap to open its binder; on the right the number in 24px with `/ total`, a `×N` badge when more than one copy is owned and a rarity pill) and an inset well with the card in a `TiltCard`: a gesture is classified once it moves 10px or lasts 200ms: a fast, mostly horizontal start is a swipe and never tilts the card; anything else tilts it in 3D up to 16 degrees with a glare that follows the finger and springs back on release. The card wobbles once when the page opens, but not after a swipe (the user wanted only the shine there). A swipe (over 50px, mostly horizontal, under 0.7s) moves to the next or previous card of the list it was opened from (set binder in number order, so missing numbers are skipped; rarity, tag and Pokémon lists; the home rail; search results); the label and card fade in (0.22s) and the shine plays again, the header shows `n / total` of that list, and the move replaces the history entry so back still returns to the list. RR and rarer cases (`isPremium` in `parse.js`, also used for the shine) get a gold hairline around the case, a gold top edge on the label and a gold rarity pill; other cards use a gray top edge and a black pill. Quantity, tags and delete live in 編輯 (the user found them odd under the card): the edit page has 重拍照片 under the photo (opens the scanner over the edit page with 取消 at the top left; auto capture and 相簿 work as usual, the straightened photo replaces the one in the form without reading text, and other fields keep their unsaved edits), the quantity field, a tag editor (removable pills and an add field) and 刪除這張卡片.
- Installed PWA: `overscroll-behavior-y: none` on `html` and `body` under `display-mode: standalone`; the home and card pages, which never scroll, also turn it off in a normal browser tab (`html:has(.page.home)`, `html:has(.page.is-fit)`), because the user did not want the home page to move at all; other pages keep the browser default there; layout heights use `100dvh` and safe-area insets.

## Scanning

- `Scanner.jsx`: rear camera (`getUserMedia`, ideal 1920x1080) under a card-shaped frame (63:88, `min(88vw, (100dvh - 230px) * 63 / 88)`, 343x479 on a 390x844 screen, slightly below center) drawn as four rounded corner brackets with the rest dimmed and no inner boxes; the hint sits in a pill below the 完成 button (「把卡片放進框內，會自動拍照」, 「換下一張卡片」 after a save, or 「拖曳、縮放照片，讓卡片在框內」 for a photo). The card only has to be roughly inside the frame: the reader searches wide areas instead of fixed boxes. 相簿 loads a photo instead; it can be dragged (one pointer) and zoomed (two pointers or the mouse wheel). The camera is requested with the rear-camera constraints first and, on any error other than a refused permission, once more with plain `video: true`. Failures show the reason from the error name with 重試 (re-request) and 相簿 still available: NotAllowedError or SecurityError (permission refused; allow the camera in the site settings; Chrome on iPhone, detected by `CriOS` in the user agent, gets the two places to fix it instead: iPhone Settings → Apps → Chrome → Camera, and Chrome Settings → Site settings → Camera, because Chrome on iOS uses WebKit like Safari but has its own app-level camera permission, and iOS does not ask again after it was refused once), NotFoundError (no camera), NotReadableError or AbortError (camera busy in another app), otherwise the raw error name; a browser without `getUserMedia` gets 「這個瀏覽器不支援相機，請改用 Safari 或 Chrome 開啟」 (Chrome on iPhone without it is on iOS below 14.3 and is told to use Safari) (typical for in-app browsers such as LINE), or a non-https note when `isSecureContext` is false.
- Live detection: every 450 ms (`LIVE_MS`) the frame area of the video or photo is shrunk to 240px wide and run through the same card detector with only the 30 best candidates fully checked (`locate` in `ocr.js`, about 43 ms per run in Node). After two hits in a row the detected card outline is drawn over the image (SVG polygon in frame coordinates), the corner brackets turn solid white and grow, the hint pill turns white with 「找到卡片，可以拍了」, and the shutter gets a soft ring. Taking a picture never waits for this. When the detector is wrong, the outline shows that before the shot.
- Auto capture: in camera mode, when the detected card has moved less than 3% of the frame (`STEADY_MOVE`) for three checks in a row (`STEADY`, about 1.3 s at `LIVE_MS` 450), the picture is taken without touching the shutter; after two steady checks the hint reads 「保持不動，馬上拍」 and the corners grow. After a saved card, auto capture stays off until the detector has lost the card once (the user took it away), so the same card is not captured twice; 重拍 turns it back on at once. The shutter still works at any time, and photo mode (相簿) never auto captures. On capture the camera video is paused, so the captured frame stays on screen and the phone can be put down; the hint pill reads 「辨識中，可以放下手機」 and a light line sweeps over the frame. The note about the first 13 MB download only shows while the models are not loaded yet (`isReady` in `ocr.js`).
- Continuous scanning: the result opens as a bottom sheet over the frozen frame (`CardEditor` with `sheet`), with 重拍 and 收進卡冊. Saving writes the card (`saveCard`), shows a white toast (「已收進 M6a 065」 or 「已經有 M6a 040，數量加 1」) and resumes the camera for the next card without leaving the scanner. 完成 at the top left (with the number saved in this session) returns home.
- On capture the frame is mapped back to video or photo pixels (object-fit cover for the video, the transformed image box for photos) and cropped to at most 1000px wide.
- Card edges (`cardDetect.js`, no OpenCV): the frame crop is shrunk to 240px wide (the thresholds are tuned for that size; 320px measured worse), blurred and run through Sobel gradients. Edge points (local gradient maxima running along the scan direction, every other scanline) vote in a Hough accumulator (slope up to 0.35 in 0.01 steps, 1px offset); up to 24 near-vertical and 24 near-horizontal peaks become candidate lines, each refit by least squares. For every line a prefix-sum profile of strong edge pixels along it is precomputed, plus profiles of four parallel lines 3 and 5 px away. Every pair of vertical and pair of horizontal lines forms a quad; it must be within 8% of the 63:88 ratio, cover 12% of the frame and have every side at least 50% covered. Its first score is mean side coverage, the weakest side, coverage just inside each corner, minus how much more the line continues past the corners than its parallel neighbours do (so a long wood-grain line is penalised but a card edge in front of dense wood grain is not), minus the ratio error, plus a little area. The best 200 (30 for the live outline) are then checked for two physical traits of a card: a rounded corner arc at each corner (radius 3.5 to 5.5% of the width) and a second parallel edge at a common inset of 2 to 5% on all four sides (the inner edge of the border); score plus arc plus twice the border match picks the card. The old rule, keeping the outermost long line per side, picked wood grain or the inner border on most framings. The quad is expanded by 1.5% and warped (homography, bilinear) to 900x1257. The saved photo is that straightened card at 630x880; when no card is found, the frame crop is used as is. On 41 framings of the five sample photos against hand-marked corners (frame 1.05 to 1.75 times the card, shifted up to 10%, kept inside the photo): corners within 8% of the card width 38 (old detector 9), within 3.5% 12 (old 0), off by more than 15% 2 (old 16, plus 2 not found); about 66 ms per run in Node.
- Text (`ocr.js`, `ocrWorker.js`): PaddleOCR PP-OCRv6 tiny (one model for Traditional and Simplified Chinese, Japanese and English) through `ppu-paddle-ocr/web` and ONNX Runtime Web, in a module Web Worker so the page stays responsive. The worker forces the `wasm` execution provider and the `cross-line` recognition strategy: by default the library prefers WebGPU when `navigator.gpu` exists, which on iPhone Safari took about 12 s per card; with WebAssembly the same build read a card in 1.1 s in the in-app browser (6.4 s before). `cross-line` batches lines into fewer recognition calls (about 20% faster in a single-thread WebAssembly run in Node) and cost one Pokémon out of 30 test reads; the detector keeps its default 960px cap because 800 and 640 lost card numbers. The detection and recognition models and the dictionary (6.4 MB, Apache-2.0, `public/models/` with `LICENSE` and `NOTICE`) are served from this site and cached by the service worker in `ocr-models`; the ONNX Runtime WebAssembly comes from jsDelivr (`ort.env.wasm.wasmPaths` set by the library, about 6.7 MB compressed, cached in `ocr-runtime`). The bundler also emits a copy of that wasm into `dist/assets`, which the app does not load. The detector finds text anywhere, so nothing needs to be aligned. The straightened card is read first; when no three-digit number was found, the unstraightened frame crop is read too and its text is added.
- `parse.js`: `parseCode` looks at each line for `NNN/TTT` (three-digit number preferred, `/` also read as `|`, `l` or `I`) and takes a rarity only from the same line right after the number (C, U, R, RR, RRR, AR, SAR, SR, UR, HR, ACE, PR). `parseDex` reads the printed Pokédex number (全國圖鑑No.0790, NO. 789) and is used before name matching. `matchName` joins CJK characters split by spaces, compares tokens with every species name (bigram Dice, plus per-character overlap for Chinese and Japanese), prefers earlier tokens, needs 0.6 (0.8 for English) and returns nothing when the two best species are within 0.05. `detectLang` says ja when there is kana, zh with four or more Han characters, en with four or more Latin words. The set code sits in a small inverted box (M6a) whose 6 looks like b, so OCR returns MbaF, JbaF or baF. `parseSetCode` takes the text before the number on the number line, drops a leading regulation mark (D to J) and a trailing single capital (F), maps look-alike letters in the digit position to digits (b to 6, O/o/D/Q to 0, l/I/i to 1, S/s to 5, Z/z to 2, B to 8, g/q to 9), upper-cases a leading lowercase letter that is not a digit look-alike (mba becomes M6a, ba stays 6a). If a set already in the binder equals the read plus one trailing lowercase letter (M6 read while M6a is in the binder), that set wins and the shorter code becomes an alternative. Otherwise it matches, in this order, the set codes already in the binder and the official Traditional Chinese set list (`src/data/sets-zh.json`, newest first): exact match with the same look-alike mapping, otherwise, only when the read ends in a lowercase letter (6a, 2a), every code ending in the same last two characters, taking the first as the answer and up to three more as alternatives (6a gives M6a, then SV6a, S6a, AS6a); a read that ends in a digit (M6a read as 60) gets no tail match, because 60 matched the old set AS6D; without any match it keeps a result shaped like `[A-Z]{1,3}\d{1,2}[a-z]?`. On 12 straightened test crops with an empty binder this gives M6a on 6 (1 to 2 before the list); the rest have no text before the number. The editor shows the alternatives as chips (也可能是), and when the set code is still empty it offers the four newest sets (最新系列); the set name from the list is shown under the field, on the binder cover and in the set summary. Empty set codes fall back to the last saved one.
- The recognition time, the number of OCR passes and the model load time are written to the browser console (`[ocr] 0.9s, 1 pass(es), model load 2.0s`) and are not shown in the UI.
- Measured in Node with the same models, detection and parsing on the five sample photos, each with the frame matching the card, 15% and 35% larger, 10% smaller (edges cut) and shifted 8% right or down (30 reads): number correct 21, wrong 0; Pokémon correct 21, wrong 0; card found 29; 0.3 to 2.3 s per card. In the in-app browser (hidden pane, production build, whole photos without any alignment) four of the photos gave the right number, name and language except a missing number on the angled dark card and RR read as R; each read took 8 to 24 s there, including the first model download. The blurry photo fails every time. The confirm screen always shows what was read and lets the user fix it. A second end-to-end run on the 41 framings above: number correct 34 with the new detector, 27 with the old one, 26 without straightening and 33 when warping with the hand-marked corners; Pokémon correct 33, 33, 31 and 32; no wrong number or Pokémon in any mode.

## Editing and data

- `CardEditor.jsx`: in the scanner it is a bottom sheet (`sheet`): grabber, the straightened card (50% wide, up to 210px), the name in 26px (「沒有讀到卡名」 in gray when none), one gray line with set code, set name, number / total and rarity, alternative set codes as chips (也可能是) when the parser was unsure, and a 修改資料 pill that switches the sheet to the full form. Only fields that were empty when the sheet opened are shown under the summary (set code with its chips and hint, or number and total), and they stay visible while typed into. The full form: set code, language (繁中 / 日文 / 英文), number, total, rarity, name with autocomplete from `names.json` in the chosen language, quantity; selects carry a drawn chevron. Editing an existing card opens the full form as a page with 儲存 in a fixed bottom bar. A new card starts from what OCR read (number, total, rarity, Pokémon from the Pokédex number or the name, language from the script, set code); set code, total and language fall back to the last saved card (`localStorage` key `lastSet`), so a pack of one set only needs the number. The buttons are never disabled: with the set code or number empty, a tap marks the missing field in red, moves the cursor there and shows 「請填寫系列代號」 / 「請填寫卡號」 above the buttons.
- `db.js` (Dexie, IndexedDB database `card-binder`): table `cards` with `lang`, `setCode`, `number` (3 digits), `total`, `rarity`, `name`, `dex`, `qty`, `tags`, `photo` (JPEG bytes as an ArrayBuffer; records saved before 2026-10-10 may still hold a Blob, and `photoBlob` in `db.js` turns either into a Blob for display and backup, because iPhone Safari can fail to store camera Blobs in IndexedDB), `createdAt` and `setKey` = `lang|setCode|total`. Saving a card whose set, number and rarity already exist adds to its quantity instead of a new entry. When saving fails, the error name and message show as a toast instead of the buttons doing nothing.
- Backup (`Backup.jsx`): everything stays in the browser on this device. 匯出備份檔 downloads `card-binder-YYYY-MM-DD.json` with photos as data URLs; 匯入備份檔 replaces all cards after a confirmation. The page shows storage use and can ask the browser for persistent storage.
- `src/data/sets-zh.json`: `[code, name]` for the Traditional Chinese expansions listed on the official card search page (asia.pokemon-card.com/tw/card-search/), newest first (136 sets, newest M6a 30th CELEBRATION; the name is the part inside 「」 plus any suffix), built by `npm run data:sets`. Only codes and names are taken, no card data or images.
- `src/data/names.json`: `[dex, zh, ja, en]` for all 1025 species from PokeAPI `pokemon_species_names.csv` (zh-Hant, ja-Hrkt, en), built by `npm run data:names`.

## PWA

- `vite.config.js`: generated service worker with `skipWaiting`, `clientsClaim` and `navigateFallback`; `src/pwa.js` checks for updates on load, when the app becomes visible, on `pageshow` from bfcache and every 30 minutes, and reloads on `controllerchange` after the first install.
